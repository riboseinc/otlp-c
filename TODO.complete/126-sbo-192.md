# TODO 126 — Encode-path audit: SBO sized for the span envelope

**Status:** Complete (v0.5.86)
**Priority:** P2 (performance: measured ~10% on attribute-bearing batches)

## What shipped

**The audit's main finding is negative, and that's the point:**
the encoder is already tight. The suspected per-attribute
malloc/free storm (a KeyValue buffer + an AnyValue buffer per
attribute, per event/link item) doesn't exist in practice —
`otlpp_pb_buf` has small-buffer optimization, and typical
attribute KeyValues (~15–25 bytes) fit the 64-byte inline buffer.
Measurement first, again.

**The real escape: the span sub-message.** A span envelope
(trace_id + span_id + name + two times + kind + flags) is
~60–80 bytes — just OVER the 64-byte SBO — so every per-span
sub-message buffer (and most event/link sub-messages with a
couple of attributes) escaped to the heap, paying malloc + the
64→128 growth copy. `OTLP_PB_SBO_SIZE` is now **192**: span
envelopes, event/link sub-messages with small attributes, and
single-record flush bodies all encode inline.

**Measured** (`otlp_bench_encode_batch`, batch=512, stable runs):
- attrs=5: ~1,090 → **~990 ns/span** (≈10%).
- attrs=0: within noise (~310–350).
- Output **byte-identical** — encoded sizes match exactly
  (30,755 / 56,355 bytes on the same fixtures) and the 20k-iteration
  encoder/messages/attribute wire properties pass unchanged.

Stack cost: `struct otlp_pb_buf` grows 64→192 inline bytes; the
deepest library-built nesting uses ~5 frames ≈ 1 KB — safe.
Exporter encode pre-sizing (v0.5.38, 256 B/span) was already in
place; the sync single-record flush paths now start inline instead
of forcing the old path.

**One test updated:** `test_buf_growth` hard-coded a 100-varint
payload sized against the old 64-byte SBO (it now fits inline, so
the growth assertion fired in Debug — Release elides asserts,
which is why only the ASAN job caught it). Now writes 300
varints; the comment records why.
